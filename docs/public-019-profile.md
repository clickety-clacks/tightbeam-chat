# Tightbeam 0.1.9 transport

This profile was checked against the released [`v0.1.9` source at `f724fc41`](https://github.com/clickety-clacks/tightbeam/tree/f724fc41089335887e6eb76bfd89d9b6d50db7cd), build `2476`. `/version.sha` reports the short stamp `f724fc41`; `PUBLIC_019_SOURCE` records the full inspected commit. The host may choose **any gateway** whose observed version, build, and short SHA match this profile. A different build, even if it reports version `0.1.9`, stays unsupported. Runtime rebuilds reject identity changes. This is source-backed capability selection, not live-gateway acceptance.

- [`router.ex`](https://github.com/clickety-clacks/tightbeam/blob/f724fc41089335887e6eb76bfd89d9b6d50db7cd/lib/tightbeam/wire/router.ex) exposes `GET /api/sessions/:sessionKey` and `/api/sessions/:sessionKey/messages?limit=50&tail=true`. The transcript collection has `items` and `page.oldestCursor`/`hasMoreBefore`. History uses opaque `before` cursors unchanged. The newest bounded slice is emitted in ascending order, displayed chronologically with the viewport at its newest end. Upward scrolling loads earlier rows without treating an agent context reset as a visibility cutoff.
- [`state_resources.ex`](https://github.com/clickety-clacks/tightbeam/blob/f724fc41089335887e6eb76bfd89d9b6d50db7cd/lib/tightbeam/state_resources.ex) emits stored `marker: {kind, from, to}` on marker rows. `harness-switch`, `model-retune`, and `session-restart` become ordered transitions. Unknown or incomplete markers fail decoding. Raw metadata remains available.
- [`change_socket.ex`](https://github.com/clickety-clacks/tightbeam/blob/f724fc41089335887e6eb76bfd89d9b6d50db7cd/lib/tightbeam/wire/change_socket.ex) authenticates `/ws/changes?protocolVersion=2`, then completes selected-session subscription before `subscription_ready`. The runtime waits for readiness before REST reads and merges buffered versioned notices with retained rows. Known turn/wake notices cause a fresh session-detail read for activity. Source-defined observational notices such as `verb.accepted` consume sequence but do not change transcript state or decide a local send outcome; the separate human socket supplies its acknowledgement. Unknown selected-session state does not establish coverage. This source-backed overlap is not a server snapshot watermark or durable event replay. Sequence gaps, disconnects, and missing heartbeats trigger a fresh subscription and REST rebuild.
- [`socket.ex`](https://github.com/clickety-clacks/tightbeam/blob/f724fc41089335887e6eb76bfd89d9b6d50db7cd/lib/tightbeam/wire/socket.ex) authenticates human `/ws` with a paired device token, then emits `sync_complete`. Sending uses that separate connection and a `c_` client ID. Correlated ack means acceptance, not agent completion. Retry retains the same ID/device/content for gateway deduplication. Session tokens can read their own selected session but cannot send through human `/ws`; org CLI tokens cannot read these routes.

The browser host keeps credentials in memory, sends REST bearer headers and WebSocket auth frames, and checks device/principal identity. It does not treat human replay as canonical history. Its local server forwards selected read routes and WebSocket frames without requiring gateway CORS support; it is a loopback development bridge, not a deployment server.

Tests cover source-shaped responses and browser interaction with a **simulated** gateway. They do not establish acceptance against a live gateway. Production hosting, token persistence, attachment operations, and token streaming are outside this example.
