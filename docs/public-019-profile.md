# Tightbeam 0.1.9 transport

This profile uses the reviewed [`0.1.9` source baseline at build `2887`](https://github.com/clickety-clacks/tightbeam/tree/0198c918dbd86861297aca19e7c3dc583943bbac) and the later [`0.1.9` source comparison at build `2908`](https://github.com/clickety-clacks/tightbeam/tree/8433d22fdf86027d62a34e9923501775225813ad). The supported floor is build `2887` and later on the same API line and protocol. The reviewed baseline supplies the endpoint, schema and capability mapping; a later build number or different full source SHA alone does not reject a target or require separate qualification. Runtime rebuilds still reject an observed identity change during that runtime lifetime. This source-backed profile is not live-gateway acceptance or proof of a running binary's full source hash.

- [`router.ex`](https://github.com/clickety-clacks/tightbeam/blob/8433d22fdf86027d62a34e9923501775225813ad/lib/tightbeam/wire/router.ex) exposes session detail, bounded message history, bounded recent turns, exact turn detail, and exact message detail. Chat reads `GET /api/sessions/:sessionKey/turns?limit=50&tail=true` for current activity and resolves an exact turn through `GET /api/turns/:seq` when a message references a turn outside that page. The turn's `messageId` and `origin` identify its authoritative trigger; Chat fetches `GET /api/sessions/:sessionKey/messages/:messageId` even when that trigger is outside the loaded history slice. Origins distinguish a person, another agent/session, and substrate activity. Optional `turnSeq` is a lookup key only; it does not prove that a reply belongs in the visible human exchange. Turn and trigger reads stay scoped to the selected generation and session.
- [`router.ex`](https://github.com/clickety-clacks/tightbeam/blob/8433d22fdf86027d62a34e9923501775225813ad/lib/tightbeam/wire/router.ex) exposes `GET /api/sessions/:sessionKey` and `/api/sessions/:sessionKey/messages?limit=50&tail=true`. The transcript collection has `items` and `page.oldestCursor`/`hasMoreBefore`. History uses opaque `before` cursors unchanged. The newest bounded slice is emitted in ascending order, displayed chronologically with the viewport at its newest end. Upward scrolling loads earlier rows without treating an agent context reset as a visibility cutoff.
- [`state_resources.ex`](https://github.com/clickety-clacks/tightbeam/blob/8433d22fdf86027d62a34e9923501775225813ad/lib/tightbeam/state_resources.ex) emits stored `marker: {kind, from, to}` on marker rows. `harness-switch`, `model-retune`, and `session-restart` remain ordered canonical transitions. Chat retains those records but hides their bubbles. Raw message metadata remains available to the host renderer.
- [`change_socket.ex`](https://github.com/clickety-clacks/tightbeam/blob/8433d22fdf86027d62a34e9923501775225813ad/lib/tightbeam/wire/change_socket.ex) authenticates `/ws/changes?protocolVersion=2`, then completes selected-session subscription before `subscription_ready`. The runtime waits for readiness before REST reads and merges buffered versioned notices with retained rows. Session and turn records update local state without rebuilding the transcript. Wake and unknown event kinds still consume sequence but do not cause extra reads, reject snapshot coverage, or replace the transcript snapshot. Source-defined observational notices such as `verb.accepted` do not change transcript state or decide a local send outcome; the separate human socket supplies its acknowledgement. This source-backed overlap is not a server snapshot watermark or durable event replay. Sequence gaps, disconnects, and missing heartbeats trigger a fresh subscription and REST rebuild.
- [`socket.ex`](https://github.com/clickety-clacks/tightbeam/blob/f724fc41089335887e6eb76bfd89d9b6d50db7cd/lib/tightbeam/wire/socket.ex) authenticates human `/ws` with a paired device token, then emits `sync_complete`. Sending uses that separate connection and a `c_` client ID. Correlated ack means acceptance, not agent completion. Retry retains the same ID/device/content for gateway deduplication. Session tokens can read their own selected session but cannot send through human `/ws`; org CLI tokens cannot read these routes.

The browser host keeps credentials in memory, sends REST bearer headers and WebSocket auth frames, and checks device/principal identity. It does not treat human replay as canonical history. Its local server forwards selected read routes and WebSocket frames without requiring gateway CORS support; it is a loopback development bridge, not a deployment server.

The surface presents only source-proven human messages and selected-agent replies. A mixed notification batch shows human member content only; non-human payload and the batch wrapper remain hidden, while the original canonical record remains available to reconciliation. Safe Markdown supplies readable headings, emphasis, lists, links, inline and block code, quotes, and tables without activating raw HTML. Tests cover source-shaped responses and browser interaction with a **simulated** gateway; they do not establish acceptance against a live gateway. Production hosting, token persistence, attachment operations, and token streaming are outside this example.
